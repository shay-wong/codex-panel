## Local build numbers

Local `app:build*` commands and `npm run tauri -- build` assign one increasing build number when Tauri packaging starts. `codex:install` reserves and prints its build number before preparing resources, then reuses that number for Tauri and streams preparation and compilation output. About shows the product version followed by `Build N`, and startup logs include the same number. macOS stores it as `CFBundleVersion`. The counter is local to the Git common directory, shared across its worktrees; source archives keep an ignored counter file at their root. It does not change the product version or update comparison. A failed attempt can consume a number. Preparing assets on their own, running development mode or starting the App does not increment it. GitHub Actions release builds retain their release version without a local build number.

本地 `app:build*` 和 `npm run tauri -- build` 在进入 Tauri 打包时递增一次；`codex:install` 在准备资源前就预留并打印构建号，后续 Tauri 沿用同号，资源准备与编译输出实时显示；“关于”显示版本及 `Build N`，启动日志带相同号码，macOS 写入 `CFBundleVersion`。计数保存在 Git 公共目录并由同仓库的 worktree 共用；源码压缩包在根目录使用已忽略的计数文件。产品版本和更新比较保持原逻辑；失败可能占用号码。单独准备资源、开发模式和启动 App 不递增，GitHub Actions 发布继续使用正式版本且不带本地号。

## New chats outside projects

**Preferences → Chat → 新聊天默认不带项目** is off by default. When enabled, ordinary new-chat actions and creation from **Recent** start without a project. Creating a chat inside a specific project still keeps that project. It does not change existing chats or explicit project choices. The adapter uses the existing one-time renderer reload on installation; later switch changes affect the next new chat immediately. See [configuration and verification](codex-compatibility.md#new-chats-outside-projects).

## Native settings presentation

While Panel is connected to Codex, open **Preferences → General → Codex 设置界面** and choose **跟随 Codex** (Follow Codex), **弹窗** (Dialog), or **整页** (Full page). Follow Codex is the default and preserves Codex's current choice. Panel saves the preference locally; reopen native settings to apply a changed choice without restarting Codex.

The native settings menu and Electron navigation entry use the same presentation choice. Direct `/settings/*` routes and dedicated links containing `account_id` keep their native full-page routing. This option changes settings presentation only; it does not change other Codex features.

The feature has its own adaptation cache. Its first preparation reuses other successfully cached modules, and the adaptation graph includes a **设置界面** (Settings presentation) node. Source matching and the native provider/menu path were checked in isolation against **Codex 26.1117.41037 / build 29803**; installed-App behavior remains a separate verification step.

## App and CLI shared sessions

The macOS and Windows launcher offers **Preferences → Models & advanced → App 与 CLI 共享会话**, off by default. Enable it with Panel connected to Codex, then run the command from **复制共享 CLI 命令** in your terminal. Panel forwards the terminal's requests and notifications through the App's existing local authenticated connection, and uses the native `retainActiveConversation` lease while a CLI view is attached. It does not remove Codex's writer lock or start another backend for that chat. The App keeps its existing transport and does not need to restart. Approvals and questions are handled in the App. Exiting with /quit or disabling sharing releases its view without canceling the App's task. Create or fork chats in the App before selecting them in the shared CLI.

普通 `codex` 启动不会自动加入共享，仍可能与 App 占用同一会话。必须使用 Panel 生成的命令，并保持 Panel 和 Codex 运行。连接凭据保存在本机描述文件，按 `0600` 模式写入，再通过子进程环境传给 CLI；复制命令不包含 token，Windows 使用其文件权限机制。macOS 隔离主流程已验证；Windows 实机和真实账号审批仍待验证。步骤、命令形式和边界见[共享会话指南](shared-sessions.md)。

## Rspack-based Codex builds

Each native adaptation feature is cached under the current Panel data directory and reused across process restarts. Its key includes the SHA-256 of the installed Codex archive contents, source-catalog revision and the adapter entry point’s actual binding dependencies, including shared helpers and parser version. File path, permissions and metadata changes do not invalidate identical contents. The content digest is streamed and reused within the process while the file metadata stays unchanged. UI, quick-phrase and media updates do not invalidate adaptation. Changing one adapter rebuilds only that feature; shared dependency changes rebuild affected features. Successful peers remain cached when a feature fails, so retries rebuild only failures. Main-window and pet-only modes share feature caches and keep separate combined plans. A combined cache hit skips native source extraction and analysis. When a feature changes in a new process, native sources are read once for that build and overlapping patches are recomposed, while unchanged features retain their cached analysis. Adopting the new cache format requires one initial rebuild. Preferences are read separately and still apply immediately. Panel establishes its base connection before preparing native adapters in the background. The launcher’s main status panel keeps the independent connection status visible while also showing source reading, currently adapting modules and final application. The adaptation area spans the card below the connection status, with module details and the progress bar together. Source reading is labeled separately, and each long resource path stays on one line with ellipsis and full hover text; the bar shows the measured percentage for the current stage; concurrent module work is combined within the adaptation stage, and stages without a known total use an activity indicator. Text remains visible alongside the bar. The same card contains a three-dimensional graph driven by the live state of each module, including repository branch prefixes. Module nodes and curved light flows distinguish waiting, adapting, prepared but awaiting application, enabled, and failed. Drag the graph to rotate it or select a node to read that module’s details. The graph keeps its height as modules are added. Only an overall ready state gathers the light flows back to the core and briefly shows success before collapsing the adaptation area. Partial or failed results retain their actual status and do not play a success completion. The graph leaves no persistent completion list. Independent features run concurrently using shared source data. Native services and update descriptors can be used as soon as they are ready; changes to already executed interface modules share one final reload. Successful features still apply when another feature fails. Pet-window preparation and background retries do not block connection handling.

各原生适配模块缓存在当前 Panel 数据目录并跨进程复用，按 Codex 安装包内容的 SHA-256、源码目录解析版本与该项入口的实际绑定依赖分别判断，包含共享 helper 和 parser 版本。路径、权限或文件属性变化不再使同内容缓存失效；内容摘要以流式读取生成，文件属性未变时在同进程内复用。普通界面、快捷短语和媒体更新不会使适配失效；修改单项只重算该项，共享依赖变化只重算受影响项。失败时保留其他成功模块，重试只处理失败项。主窗口与仅宠物模式共用模块缓存，分别保存最终组合；完整命中时跳过源码提取和分析。新进程中有模块变化时仍需读取一次原生源码并重新合成重叠补丁，未变化模块复用已有分析。首次采用新缓存格式需重建一次。偏好仍独立读取并即时生效。Panel 先建立基础连接，再在后台准备适配。启动器顶部状态模块上方始终保留独立的连接状态，下方以完整宽度将进行中的源码读取、当前模块及最后应用文字与进度条放在一起，资源读取单独标明阶段，长资源路径保持单行并在悬停时显示全文，显示当前阶段的真实处理百分比；并发模块在适配阶段汇总，无可计数总量的阶段显示活动状态。同一状态卡内的三维图谱由各模块真实状态驱动，包括仓库分支前缀。模块节点和弧形光流区分等待、适配中、已适配待应用、已启用及失败；拖动可旋转图谱，点击节点查看该模块详情，模块增加时图谱高度不变。仅整体就绪后光流汇回核心，短暂显示成功再收起适配区域；部分成功或失败保持实际状态，不播放成功完成动画，不常驻完成清单。独立能力共用源码并发处理，原生服务及更新描述准备好后即可使用；已经执行的界面模块最后统一刷新一次。某一能力失败不影响其他成功项，宠物窗口准备和后台重试不阻塞连接处理。

## Repository branch prefixes

While Panel is connected, open native **Settings → Git → Branch prefix → Configure by repository…**. The dialog lists configured repositories with their names, editable prefix fields, workspace paths, and **Delete** actions. Edit the prefix directly in its row; leaving the field or pressing Enter saves it. Leave the field empty to save **No prefix**. Choose **Add** to select a repository that is not yet configured, then choose **Custom prefix** (for example, `team/`) or **No prefix** and save to return to the list. **No prefix** is an explicit override: new chats are instructed to create branches without the native `codex/` default, and suggested branch names omit it. Repositories without a configuration use the native global value; **Delete** removes only that repository's override and restores this behavior.

Overrides are saved locally in the current Codex profile and do not synchronize between profiles or devices. Panel uses the target chat's native repository identity and host, so conversations and worktrees assigned to the same repository share its prefix. Without a chat assignment, it matches that workspace's path and host to a configured repository root. Switching the selected repository does not rewrite the global setting. The choice applies to newly created chats and native branch-name suggestions. When Codex normally resumes a chat and rebuilds its Git instructions, Panel reads the repository mapping again using that chat's assignment. Active subscribed chats and native resume modes that retain server instructions may keep an earlier prefix; start a new chat to ensure the current choice applies. An explicit branch name or prefix requested in a chat takes precedence. Custom prefixes accept up to 200 characters and cannot contain whitespace or Git special characters; saving an invalid value displays an error without replacing the saved choice.

The native source path and isolated local flow are verified separately from installed-App use and real model-created branches.

## Quick phrases

Successful results are cached for 24 hours, temporary failures for 5 minutes, and API rate limits until GitHub's reset time. It accepts only normalized `vX.Y.Z-fork` candidates and exact HTTPS release-tag URLs. Available updates are downloaded and signature-verified in the app, then installed only after user confirmation. ## Reliable initial Codex injection

The standalone launcher waits up to 30 seconds for Codex's main renderer after CDP becomes reachable. It ignores auxiliary renderers such as global dictation and the avatar overlay, then waits for the main renderer's initial `app://` document to reach `complete`. Only then does it enable the CSP bypass and reload once, allowing the registered document-start injection to run without aborting the official desktop bootstrap. The automatic Panel-open request is a one-shot latch claimed by the first available main renderer, so a later iframe failure keeps the supervised service and manual retry available without repeatedly overriding native conversation navigation.

Chromium 151 applies Local Network Access checks to loopback subframe navigation. The manager-owned injector therefore passes `--disable-features=LocalNetworkAccessForSubframeNavigations`, and the managed iframe delegates `local-network-access`, `loopback-network`, and `local-network`. The compatibility switch is limited to subframe navigation; fetch, WebSocket, and other Local Network Access checks are not disabled.

Run the launcher as documented in [Embed in Codex](../README.md#embed-in-codex):

```bash
CODEX_PANEL_HOST=127.0.0.1 npm run codex
```

The wait duration is fixed. If no main renderer appears within 30 seconds, the launcher exits with `Timed out waiting for a Codex renderer target`.

Jira settings can enable automatic completion, which remains off by default. A Jira requirement is eligible only when it has at least one linked execution issue and every linked issue is unarchived and done. It rereads Jira after the transition to confirm the final state. If Jira changed after the last Panel sync, the requirement detail offers **Accept remote** and **Complete anyway** instead of overwriting the remote edit. Temporary server, timeout, or rate-limit failures retry twice; final failures keep local issues done and expose **Retry**.

Jira settings can enable automatic conversation archiving, which remains off by default. When enabled, Panel archives the Jira planning conversation and the Panel-managed execution conversations associated through simple start, automatic claiming, or rework after Jira and every linked execution issue are done. Archived conversations leave the active list but retain their local thread, run, event, and Codex thread records for direct historical reads. A currently running turn remains visible until it settles. ## Persistent automatic execution queue

Tickets from the same Jira requirement and repository execute sequentially in one native Codex conversation, branch, and worktree. The first ticket creates the worktree through Codex; subsequent tickets resume the saved conversation with structured Skills and retain its permissions and workspace. Each ticket still has its own binding, activity, status, and attempts. An active or blocked execution holds the group's next ticket. Same-repository prerequisites with an execution binding can unblock the next ticket at `in_review`; other dependencies wait until completion. Only authorized work is released, and a pending Jira decision or paused project still prevents dispatch. With a published plan, reuse stays within its current ticket set; reopened work does not adopt completed historical conversations. Existing separately bound tickets retain their bindings rather than moving code or messages automatically.

A busy native conversation uses the existing bounded retry policy, while a missing or mismatched workspace stops execution instead of creating a replacement. When the original conversation binds itself and takes over after a launcher timeout, Panel reconciles the queue with its actual status and clears the stale current error; historical comments and attempts remain. Upgrading removes the queue's old one-conversation-per-ticket uniqueness constraint without deleting records. Shared worktrees are retained while their group has unfinished tickets.

When older tickets already have different execution conversations, Panel prefers the current ticket's bound direct prerequisite. If no unique execution context can be selected, it asks for an explicit conversation binding rather than choosing an arbitrary worktree. Disabling automatic claiming still releases authorized dependencies to `todo` for **Prepare execution**, without automatically enqueuing them.

Native conversation entries in issue activity use the board's session-progress polling, including conversations shown in an open detail even when the issue is not in progress. Running and idle reflect the actual conversation; unavailable session data displays **Status unknown**. This display does not move issues or modify the execution queue.

Each repository project has a Panel-owned automation policy stored with the local Panel database. The automation menu can enable or disable automatic claiming, pause all dispatch for the project, choose a 5, 10, 15, 30, or 60 minute scan interval, and select the model and reasoning effort. It also sets the global default project parallelism, which starts at 3 and accepts 1 through 8, and lets the current project follow that default or override it with another 1-8 value. Projects do not share a total device limit. The menu shows queued, running/effective-capacity, blocked, and failed totals. Jira and Cloud projects do not expose this policy.

Automatic scans queue waiting local issues that are not linked to Jira. A Jira-linked execution issue enters the queue only after its Jira requirement is in progress and has no pending lifecycle decision. **Prepare execution** opens an unsent draft with Manage Panel, which reads applicable workflow stages after inspecting the issue. Choose **Current directory** (default) or **New worktree**; existing conversation and development bindings are reused. Preparation does not queue or claim the issue. Only a confirmed user submission binds the actual Codex conversation and workspace and moves the issue to `in_progress`. Automatic claiming and Jira simple-start continue to submit automatically. Disabling automatic claiming stops new automatic entries but lets the current queue drain; pausing a project keeps every queued item waiting until the project resumes.

Preparation selects the project and run location before filling the composer. Pending manual drafts pause native automatic dispatch so the queue cannot overwrite the draft. Manual preparation errors leave the issue unchanged; automatic dispatch errors say that startup was not confirmed, while failures of a running attempt remain execution failures.

During manual execution, the detail action shares the board's conversation activity: **Processing · Open conversation** while running, or **In progress · Open conversation** otherwise. Clicking opens the saved conversation without preparing another execution. Returning the task to waiting restores **Prepare execution**. For local tasks, **Open in new conversation** remains available even with a saved conversation: Panel actively opens a new composer in the selected repository, waits for it to appear, and inserts the task and latest handoff without reading the old conversation. The first manual send updates the task binding. Continue planning and Prepare execution still reuse the saved conversation; SSH and Jira-specific entries retain their existing lifecycle.

The queue persists its source, state, selected conversation, attempts, next retry time, and last error. Dispatch prefers manual and resumed work; Jira-authorized and scanned work then share the issue-priority and board-order queue. Capacity keeps an issue waiting in `todo`. Codex therefore owns worktree creation and runs the project's configured environment setup; Panel stores the actual native thread binding, worktree path, and branch only after Codex returns them. Jira-linked execution uses the Jira external key in its task title, prompt, and branch naming instruction instead of the Panel issue identifier. Completed work enters `in_review`; only user acceptance authorizes `done`. Execution that needs input shows **Waiting for your reply** and resumes only after a user comment or completed user turn. Other execution failures show **Prepare again** for an explicit retry, while automatic scans ignore blocked work. Jira-paused work stays disabled until its Jira requirement returns to in progress. Transient connection or startup failures retry after 30 seconds and 2 minutes.

A service restart records the interrupted attempt and returns the issue to waiting. It resumes only when the stored conversation, execution history, and development context still agree; uncertainty blocks the issue instead of creating another conversation. Worktrees remain attached through `in_review` and are removed after `done` only when clean and merged into `origin/main` or local `main`. These limits apply only to Panel-managed one-click and automatic execution. Panel does not limit, scan, or change user-created Codex tasks or Scheduled Tasks, except that migration may pause the one exact legacy automation ID previously saved by Panel.

Same-direction updates retain velocity; reversals reset the previous velocity to zero before accelerating toward the new target. ## Codex updates through Panel

The macOS update card lists upgrade targets with a direct delta from the installed build. When available, the newest build marked **已验证源码适配** is selected by default. That label records source adapter checks for the exact version, build, and architecture. The installation confirmation names the selected version. If Codex's own updater is downloading or waiting to install, Panel asks the user to resolve the conflict before quitting Codex.
